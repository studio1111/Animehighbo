# مشخصات فنی بازسازی Animehighbot
تاریخ: 2026-10-21  
مخزن: `studio1111/Animehighbo`

## هدف و معیارهای پذیرش
بازسازی متمرکز گردش‌کار آماده‌سازی و انتشار قسمت‌ها به‌گونه‌ای که:
- هر قسمت مستقل آماده شود و شکست آن به قسمت‌ها یا انیمه‌های دیگر سرایت نکند.
- هر بسته فقط پس از آماده‌شدن و اعتبارسنجی پوستر، اطلاعات، سه کیفیت 1080p/720p/480p و ترک‌های زیرنویس انگلیسی و فارسی قابل انتشار باشد.
- انتشار قسمت‌های یک انیمه به ترتیب شمارهٔ قسمت انجام شود؛ انیمه‌های متفاوت نباید یکدیگر را معطل کنند.
- هر بستهٔ واجد شرایط بدون انتظار برای پایان batch یا موفقیت Workerهای دیگر به صف انتشار برسد.
- تکرار اجرای workflow، خطای موقت شبکه یا اجرای هم‌زمان موجب انتشار تکراری تا حدی که Telegram API و وضعیت ذخیره‌شده اجازه می‌دهند نشود.
- فایل‌های خروجی واقعاً قابل خواندن باشند، مدت معقول ویدئو و ترک‌های مورد انتظار را داشته باشند و اندازهٔ فایل با محدودیت مقصد سازگار باشد.
- README با رفتار واقعی پروژه همسان باشد و آزمون‌ها، به‌ویژه آزمون‌های جداسازی خطا و ترتیب، این قرارداد را پوشش دهند.
- هیچ قابلیت یا دادهٔ انتشار قبلی حذف یا بازنشانی نشود.

## معماری
### 1. آماده‌سازی مستقل
Workflow آماده‌سازی، ورودی‌های مجاز را کشف کرده و برای هر قسمت یک اجرای مستقل می‌سازد. هر اجرا فقط مسئول یک قسمت است؛ خطای دانلود، استخراج زیرنویس، ترجمه، encode، پوستر یا اعتبارسنجی همان قسمت را به حالت شکست/نیازمند تلاش مجدد می‌برد و خروجی ناقص را به ناشر تحویل نمی‌دهد. شکست یک اجرای ماتریس نباید اجرای قسمت‌های دیگر را لغو کند یا انتشار بسته‌های سالم را پشت شرط موفقیت کل ماتریس نگه دارد.

### 2. قرارداد بستهٔ آماده
بستهٔ تحویلی باید شامل manifest نسخه‌دار، شناسهٔ پایدار قسمت، عنوان/شماره/تاریخ منبع، metadata و caption پوستر، تصویر پوستر، سه فایل ویدئو، اطلاعات codec/مدت/اندازه و SHA-256 همهٔ فایل‌ها باشد. هر سه ویدئو باید حاوی ترک انگلیسی و فارسی باشند. ناشر قبل از انتشار، مسیرها را محدود به پوشهٔ بسته نگه می‌دارد، هش‌ها را تطبیق می‌دهد، فایل‌های الزامی و اندازه/مدت/ترک‌ها را دوباره بررسی می‌کند و بستهٔ ناقص را رد می‌کند.

### 3. صف پایدار انتشار و تقدم قسمت‌ها
صف انتشار از وضعیت نسخه‌دار پایدار ساخته می‌شود و به موفقیت اجرای آماده‌سازی یا batch دیگر وابسته نیست. بسته‌های آماده برای انیمه‌های مختلف مستقل هستند. برای هر هویت سری/فصل، قسمت N فقط زمانی eligible است که تمام قسمت‌های پیشین شناخته‌شده در manifest که باید قبل از آن منتشر شوند، وضعیت انتشار کامل داشته باشند. قسمت N+1 در انتظار می‌ماند، اما این انتظار نباید صف سایر انیمه‌ها را متوقف کند. پس از تکمیل انتشار قسمت پیشین یا رفع مانع، صف دوباره ارزیابی می‌شود.

اگر شمارهٔ قسمت یا هویت سری مبهم باشد، سیستم نباید ترتیب را حدس بزند؛ بسته را برای بررسی/اصلاح metadata نگه می‌دارد و سایر بسته‌ها را ادامه می‌دهد. شمارهٔ فصل باید بخشی از هویت سری باشد تا قسمت 1 فصل جدید با قسمت 1 فصل قبل اشتباه نشود.

### 4. ناشر تلگرام و وضعیت
ناشر مستقل فقط بسته‌های کامل و واجد شرایط را انتخاب می‌کند. برای هر قسمت ابتدا یک پوستر با caption کامل می‌فرستد و سپس سه کیفیت به‌ترتیب 1080p، 720p، 480p را به‌صورت reply به همان پوستر ارسال می‌کند. هر شناسهٔ پیام بلافاصله پس از موفقیت ثبت می‌شود. حالت‌های جزئی (پوستر ارسال شده، کیفیت‌ها ارسال شده) حفظ می‌شوند تا تلاش مجدد از آخرین مرحلهٔ تأییدشده ادامه یابد. قبل از ارسال، قفل منطقی/محدودیت هم‌زمانی روی وضعیت مشترک اعمال می‌شود؛ در صورت تعارض هنگام ذخیره‌سازی، وضعیت جدیدتر هرگز بازنویسی نمی‌شود.

### 5. سیاست Gemini
فقط یک Secret اصلی `GEMINI_API_KEY` برای ترجمه استفاده می‌شود. پاسخ 429 با همان کلید و backoff محدود و رعایت `Retry-After` دوباره امتحان می‌شود؛ اگر خطا ادامه یافت، همان قسمت fail-closed می‌شود و ترجمهٔ ناقص یا خروجی بدون زیرنویس معتبر منتشر نمی‌شود. کلیدهای جایگزین و مترجم آفلاین به‌عنوان fallback خودکار استفاده نمی‌شوند. شکست Gemini هیچ اثر سراسری بر آماده‌سازی/انتشار انیمه‌های دیگر ندارد.

### 6. GitHub Actions و منابع
- Workflowهای آماده‌سازی و انتشار جدا هستند؛ تحویل با artifact کوتاه‌عمر به‌همراه صف/manifest پایدار انجام می‌شود.
- ناشر با رویداد تکمیل آماده‌سازی یا اجرای بازیابی صف فعال می‌شود؛ نباید به triggerای تکیه کند که artifact آن دیگر در دسترس نیست.
- concurrency باید ناشر را در برابر race محافظت کند، ولی نباید یک اجرای آماده‌سازی ناموفق یا صف قدیمی را به مانع دائمی اجراهای بعدی تبدیل کند.
- نگهداری اجرای workflow مطابق قانون موجود: فقط 30 اجرای تکمیل‌شدهٔ آخر نگه داشته شوند؛ اجراهای فعال حذف نشوند.
- راهکار باید در GitHub Actions و بدون سرور پولی یا پایگاه دادهٔ Supabase اجباری کار کند. بررسی فعلی اتصال Supabase هیچ پروژه‌ای برنگرداند؛ بنابراین صف پایدار از داده‌های موجود مخزن/آرتیفکت‌ها استفاده می‌کند و وابستگی جدیدی به Supabase ایجاد نمی‌شود.

## ایمنی داده و سازگاری
- `data/state.json` و `data/archive_manifest.json` موجود باید حفظ شوند؛ هیچ reset یا حذف پیام/سوابق انجام نمی‌شود.
- هویت‌های قدیمی و شناسه‌های پیام موجود باید با migration سازگار یا با fallback محافظه‌کارانه حفظ شوند.
- هیچ secret در فایل‌ها یا logها چاپ نمی‌شود.
- تنها ورودی‌هایی پردازش می‌شوند که مجوز دانلود و بازنشر آن‌ها تأیید شده باشد؛ این spec مجوز حقوقی جدیدی ایجاد نمی‌کند.
- اگر ارسال تلگرام بعد از دریافت موفق پاسخ شبکه قطع شود و شناسهٔ پیام در اختیار سیستم قرار نگیرد، تضمین exactly-once مطلق ممکن نیست؛ سیستم باید از duplicate-risk جلوگیری کند و حالت مبهم را ثبت کند تا بدون ارسال کورکورانه قابل بازیابی باشد.

## آزمون‌ها و اثبات آمادگی
1. آزمون‌های واحد برای انتخاب صف، شناسایی فصل/قسمت و جلوگیری از انتشار قسمت بعدی پیش از قسمت قبلی.
2. آزمون چند انیمه: خطای ترجمه/encode در A-1 مانع انتشار B-1 نشود؛ A-2 تا انتشار A-1 منتظر بماند.
3. آزمون بستهٔ ناقص، checksum نامعتبر، فایل خراب، مدت صفر/غیرمنطقی، ترک زیرنویس غایب و بیش‌ازحد بودن حجم.
4. آزمون خطاهای Telegram پس از پوستر یا هر کیفیت و ادامه از مرحلهٔ درست بدون تکرار پیام‌های ثبت‌شده.
5. آزمون تداخل دو ناشر و تعارض ذخیرهٔ وضعیت.
6. آزمون قرارداد workflow، مجوزهای حداقلی، path filters و retention 30 اجرا.
7. اجرای کل آزمون‌ها، بررسی lint/compile و اعتبار YAML.
8. اجرای workflow آماده‌سازی و ناشر با یک بستهٔ مجاز واقعی؛ بررسی گزارش اجرا و تأیید در کانال که پوستر و هر سه فایل با زیرنویس درست منتشر شده‌اند. CI سبز به‌تنهایی اثبات انتشار نیست.

## محدودهٔ تغییر
اصلاح هدفمند `app.py`، `tools/episode_queue.py`، ابزارهای زیرنویس/encode/manifest در صورت نیاز، workflowهای GitHub Actions، تست‌های مرتبط، دادهٔ صف پایدار در صورت نیاز و README. ابتدا همهٔ callerها، workflowها، تست‌ها و قراردادهای موجود بررسی می‌شوند؛ تغییرها به‌صورت TDD و با حفظ state فعلی انجام می‌شوند.

## معیار پایان
کار فقط وقتی کامل محسوب می‌شود که تست‌ها سبز باشند، workflow آماده‌سازی و انتشار از هم مستقل باشند، یک انیمهٔ خراب انیمه‌های دیگر را متوقف نکند، ترتیب قسمت‌های همان انیمه حفظ شود، README به‌روز باشد و انتشار واقعی یک بستهٔ کامل در تلگرام از گزارش workflow تأیید شود. اگر مجوز/دسترسی/سهمیهٔ بیرونی مانع تست زنده شود، این مانع صریح ثبت می‌شود و نباید انتشار موفق ادعا شود.
